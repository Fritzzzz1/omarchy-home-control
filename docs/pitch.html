Decision memo · omarchy-home-control

Home Control, packaged.

You built the voice channel. This is about the box it now ships in — what that bought you, what it cost, and the three things it still cannot do.

The claim

Home Control is now a git-cloneable Omarchy plugin with a reversible installer, and no line of it names your machine.

The catch

An Omarchy plugin is QML inside omarchy-shell. Home Control is a node daemon. It does not fit; it sits alongside.

Untested

Nothing was installed, enabled or started. Two claims on the next slides are argued, not observed.

01

What it does

Four moving parts, one of them optional

valid The plugin

manifest.json + Panel.qml. A bar widget: microphone glyph, dim when the unit is down, red when it failed. Click opens the phone URL, right-click starts it if it is stopped, middle-click re-polls.

Passes omarchy-plugin-validate — Omarchy's own schema checker, the same code path the shell uses before it will load anything.

dry-run tested The installer

install.sh writes the app, a venv, the state dir, one config file, the systemd user unit, and the tailscale serve mapping. Every step prints under --dry-run before it touches anything.

It refuses to install when the unit is live or the port is occupied. Verified: it refused on this box, because 4455 is yours.

run against live home-control-ctl

status --json, doctor, logs, url. The single place that knows the wiring — the widget shells out to it and knows no ports or hostnames itself.

Pointed at home-voice.service it correctly reported your running channel as active and reachable, without touching it.

unexercised The distribution path

omarchy plugin add <git-url> --enable clones, validates, refuses reserved ids and symlinks, then enables.

That gives a stranger the widget. It does not give them Home Control — they still run install.sh. The README says this in the first paragraph rather than burying it.

No symlinks anywhere — Omarchy's validator rejects a plugin folder containing even one, because a symlink could point the trusted plugins directory back at arbitrary files.

The manifest, in full

{ "schemaVersion": 1,
  "id": "omarchy.home-control",
  "kinds": ["bar-widget"],
  "entryPoints": { "barWidget": "Panel.qml" },
  "barWidget": {
    "defaultSection": "right",
    "defaults": { "unit": "home-control.service",
                  "refreshIntervalSec": 10 },
    "schema": [ /* generates the settings form */ ] } }

One subtlety worth knowing

Manifest defaults are not merged into the widget's settings at runtime — they only seed the settings UI. Every default is restated in the QML. First-party widgets do the same; skipping it is the classic way to ship a widget that silently reads undefined.

03

How it is built

Why a hybrid, and not a plugin

This is the part a dishonest pitch would skip.

The mismatch, stated plainly

Omarchy's plugin kinds are bar, bar-widget, menu, overlay, panel, service — and service means a QML singleton inside the shell process, not a systemd unit. There is no kind that means "ship me a daemon". So the format cannot carry Home Control, only a view of it.

Why this is still the right container

A plugin folder is just a git repo that must contain a valid manifest. Nothing forbids it also carrying an installer, a unit template and the app. You get Omarchy's clone-validate-enable path for free, and a bar presence that is genuinely idiomatic, without pretending the daemon is a widget.

No root, anywhere

Nothing outside $HOME except the tailnet mapping, which belongs to your tailscale login. No pacman, no /etc, no system unit. There is no passwordless sudo on this box and the installer never wants any.

The config is the whole surface

The unit carries no Environment= lines at all — it reads one EnvironmentFile, without the - prefix, so a missing config is a loud failure rather than a service quietly starting on wrong defaults.

Reversal is the default

uninstall.sh removes the unit, the serve mapping and the command, and keeps your transcript, passphrase and venv unless you ask for --purge. It never touches VOICE_ROOT, never disables linger, never removes node or claude.

06

Boundaries

What it does not do

unverified It has never been started

I did not install, enable, or start anything, and did not restart home-voice — it is still up with NRestarts=0.

So two claims are argued, not observed: that the service comes up cleanly from the rendered unit, and that the widget renders in your bar. What was checked: systemd-analyze verify clean on a throwaway copy, qmllint exit 0, omarchy-plugin-validate exit 0. Those catch syntax and schema, not runtime.

by design The widget will not stop it

Right-click starts the service when it is down. There is no stop and no restart on the bar, at all.

The claude process talking to whoever is on the phone is a child of that service. A misclick on a status icon must not be able to hang up on your father mid-sentence. home-control-ctl restart does it, and asks first.

not done The phone still says "Home"

Branding is untemplated in four files: app/index.html, app/login.html, app/monitor.html, app/manifest.json — titles, the <h1>, the iOS home-screen name.

Only the persona (voice-mode.md) is rendered per-install. Templating four HTML files was scope I did not think earned itself; it is a rename, not a redesign.

not done The plugin alone is inert

omarchy plugin add gives someone a bar icon that reports "not installed" and does nothing else. The service is a separate, explicit step.

That is honest but it is not a one-command story. If you want one command, the plugin would have to shell out to install.sh on enable — which means a shell plugin silently building a venv and claiming a port. I would not ship that.

07

Boundaries

One capability, and the line under it

Setup asks exactly one question, and the default answer is no.

opt-in · default off The question

May the agent use ListAgents to find another live Claude Code session on this machine, and hand it work this conversation lacks the tools for?

Never enabled silently. Asked aloud, or set with --peer-delegation on|off; a non-interactive install leaves it off. Recorded as a plain flag, VOICE_PEER_DELEGATION, in config.env — inspectable and revocable.

ListAgents and SendMessage are Claude Code's own tools, so the installer skips the question entirely when there is no claude on PATH rather than asking something meaningless.

Off is a gate, not a preference

The voice server passes a closed --allowedTools allowlist. So the flag does real work: on appends ListAgents and SendMessage to it, off leaves them absent and the agent simply cannot reach them.

Worth saying plainly: prose in the persona file alone would have achieved nothing here. That is why this landed as a 20th entry in parameterise.py rather than a paragraph.

The rule, written down rather than implied

A missing tool is a reason to delegate. A denied action is not.

Delegating because this conversation lacks a tool is legitimate — the work needs something this session cannot do, and a peer can. Delegating because you refused something, or because the agent expects its own permissions would block it, is not. Permission boundaries are per-session: a peer acting on the agent's behalf does not inherit your consent, it steps around a decision you already made. Work that was refused goes back to you, never sideways to another agent.

It is in the setup prompt, the README, and the agent's own instructions — in the off case too, where it is told plainly that it may not, and why. Honest about the reach: the flag gates the tools; when to use them rests on the agent following the rule. And the wording is rendered at install time, so flipping the flag by hand changes the tools at once while the written instructions still describe the old state — re-run install.sh to resync.

Version assumptions

Written against Omarchy 4.0.0.alpha and Quickshell 0.3.1, plugin manifest schemaVersion 1. The widget imports qs.Ui / qs.Commons and inherits BarWidget — internal Omarchy API with no stability promise. An alpha that renames BarIconButton breaks the icon; it does not break Home Control.

The whisper endpoint is not included, and cannot be

--whisper-url is required with no default, because there is no honest one. This app runs no local model — it POSTs to a whisper.cpp server's /inference.

Yours is the Mac mini. A stranger has neither that box nor that tailnet, so they must stand one up or point at their own. This is the single biggest thing between "cloned it" and "it works".

The phone page needs the internet

onnxruntime-web and @ricky0123/vad-web load from jsdelivr, plus a Google font. Offline, or behind a strict CSP, voice input dies and the page falls back to typing. Vendoring them is the fix and it means editing your live index.html — so I left it and wrote it down instead.

Linux only

systemd user units, loginctl, pactl/paplay. The Mac's launchd half of this story is not in the repo.

09

Decision

What I would do next, in order

1 · Prove it starts — on a second port, once

./install.sh --port 4465 --tts-port 4467 --label test, watch it come up, then ./uninstall.sh --purge. That converts the single biggest unverified claim into an observed one and never goes near 4455 or your running channel.

2 · Enable the widget and look at it

Plugin code under ~/.config/omarchy/plugins/ hot-reloads on save — no shell restart. If it fails to load, journalctl -t omarchy-shell prints the exact errorString().

3 · Only then decide about distribution

Nothing is published. No remote is configured on the repo. That stays true until you say otherwise.

The honest summary

The packaging did real work: 19 hardcoded values removed, a reversible installer with a dry run, a control command, and a validated plugin manifest. Your app is genuinely no longer welded to this machine.

It did not make Home Control one-command installable for a stranger, and it could not — the whisper dependency and the QML/daemon mismatch are both structural, not laziness.

And it is a package that has never been unpacked. Everything above was verified by validators and syntax checkers, against a live service I was careful not to disturb. The first real test is fifteen minutes on a spare port.
